## Experiment and measured results

The official scaffold was run offline against the prepared ROM with one player, no submodule downloads, no recomp-ui, no netplay, no CI, no artwork fetching, no remote repository creation, and generation/build deferred. The source pin was then recorded explicitly. The shared beam-aligned driver is used unchanged.

Analysis uses only the scaffold's hardware-vector seeds and two source labels. It disables HLE emission and does not import stock SMW CFGs. `funcs.h` is generated before compilation. First emission produced **47 exact AOT variants from 4 roots across 7 banks**, with 60 demand edges. The measured invocation took about **0.4 seconds**, with maximum RSS about **34 MiB**, within the 600-second/4-GiB limit. These are the proven static frontier, not whole-game coverage. A repeat emission verified cached output and reused all seven banks.

The prototype executable is:

```text
local/build/demo-1-1/BrutalMarioDemo11SNESRecomp
```

The shared input route (`recomp/inputs/m1-route.script`) starts a fresh session, reaches the title/file menu, dismisses the opening message with A, enters level $105, moves right, and attempts jumps. It runs **6,104 guest-frame calls** and exits normally in both hosts. The route falls into a pit and returns to the overworld with one life lost; it is a smoke route, not a level-clear test. No savestate imports or WRAM pokes are used. The native run adds only a zero-frame `turbo on` host command to remove wall-clock pacing.

Instrumented native results: **53,155 compiled-body bridge entries** and **81,826,973 interpreted opcodes**, approximately 63 seconds for the full route on this host. These counters have different units: they do not establish a percentage of compiled instructions. The prototype still relies heavily on interpretation.

Coverage records contain **652 distinct sites**, with no dropped cost samples, tuple overflow, RAM-routine overflow, or journal write failures. Runtime execution is confirmed at WRAM **$7F8000, $7FFFF0, and $7EC130**. This validates WRAM execution as a target requirement, without proving a particular supplied ASM file's binary correspondence.

Two native coverage captures produced identical full WRAM snapshots and exact framebuffer bytes at all eight scene samples. Reference audio was captured as stereo 32,040-Hz PCM with nonzero samples; native audio playback/fidelity has not been qualified (the automated host uses SDL dummy audio).

## Comparison findings

Capture comparisons are reproducible using `tools/compare_captures.py`. Snes9x reports RGB565 and expands it to BGRX; native rendering produces BGRX directly. The table uses a common 5-bit-per-channel grid to remove conversion differences. Each frame has 57,344 pixels. This is scene sampling, not proof of full frame-by-frame equivalence.

| Scene | Host frame | Pixels differing after RGB5 quantization | Reference player X,Y | Native player X,Y |
| --- | ---: | ---: | --- | --- |
| Title | 600 | 0 | 2,144 | 2,144 |
| File menu | 783 | 0 | 2,144 | 2,144 |
| Opening message | 1,686 | 321 | 128,352 | 128,352 |
| Overworld | 2,108 | 5,556 | 13,286 | 13,286 |
| Level entry | 2,319 | 774 | 64,352 | 64,352 |
| Walking | 2,380 | 837 | 172,353 | 172,352 |
| Pit/death segment | 2,504 | 16,214 | 243,677 | 246,702 |
| Endurance end | 6,104 | 5,725 | 13,286 | 13,286 |

Even at the visually matching title, WRAM $13/$14 counters differ: reference `23/c1`, native `37/d5`. Later deltas grow. Therefore host-frame numbers do not yet establish equal guest simulation phase. Timing, frame-boundary, and input-latch alignment must be investigated before declaring gameplay fidelity or changing game logic. The earliest differing **sampled picture** is the opening message; the exact first divergence has not been located.

Opening-message glyphs look garbled in both hosts. This may be original/incomplete content or a compatibility issue; no conclusion is drawn without the ZSNES baseline.

### Compiled versus interpreter-only diagnostic

An initial `SNESRECOMP_LLE_BOUNCE=0` run still entered compiled bodies (52,964 entries). In this driver the flag alone does not disable every bounce path; that run is **not** an interpreter-only baseline.

The corrected diagnostic excludes every generated manifest PC and its LoROM mirror using the upstream `SNESRECOMP_LLE_INTERP_TARGET_FILE` gate. Its measured counters are **0 compiled-body entries** and **84,955,845 interpreted opcodes**, and it also completes 6,104 frame calls normally. Exact framebuffer bytes match the compiled-enabled run at all eight scene samples, and the sampled mode, level, player coordinates, lives, and $13/$14 counters match. Full WRAM is not identical: sampled differences occupy stack-page addresses and remain recorded rather than masked. This is not a proof of complete translation equivalence.

The reference/native frame-counter discrepancy therefore also occurs without compiled guest execution. Prioritize the shared frame/hardware timing and cross-core phase alignment; the specific cause is still unknown. Full comparison data is in `local/reports/aot-floor-comparison.json`, with an aggregate in `local/reports/m1-summary.json`.

## Reproduction

Fetch the three repositories into their `local_path` values from `config/upstreams.json`, then check out the exact commits. No recursive submodules are needed for this single-player, no-launcher experiment. Keep the upstream licenses in their checkouts. Install the pinned Rust toolchain locally or use an existing installation of that exact toolchain.

From the project root:

```sh
mkdir -p local/reports
python3 tools/prepare_rom.py --base '../roms/Super Mario World (U) [!].smc'
python3 tools/m1.py check

# Only for a fresh experiment; an existing directory is deliberately refused.
python3 tools/m1.py scaffold

# When using this workspace's project-local Rust installation:
CARGO_HOME="$PWD/local/toolchains/cargo" \
RUSTUP_HOME="$PWD/local/toolchains/rustup" \
PATH="$PWD/local/toolchains/cargo/bin:$PATH" \
python3 local/upstream/snesrecomp/tools/build_native_analyzer.py --test

python3 tools/m1.py generate
python3 tools/m1.py build

cmake -S local/upstream/snesrecomp/tools/snesref \
  -B local/build/snesref -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build local/build/snesref --parallel 2
make -C local/upstream/snes9x/libretro -j2

# Choose fresh names; capture directories are never overwritten.
python3 tools/m1.py reference --capture reference-new
python3 tools/m1.py native --capture native-new
python3 tools/compare_captures.py \
  local/captures/reference-new local/captures/native-new

# Optional isolated translation diagnostic; verifies zero compiled entries.
python3 tools/m1.py native --interpreter-only --capture native-floor-new
```

`tools/m1.py` rejects changed upstream revisions, modified tracked upstream files, license-digest mismatches, and an unexpected target ROM. The generation stage applies memory/time limits. The build stage installs project-owned exit counters into the local host shim; upstream sources and generated C are not edited. Runtime working directories are isolated under each capture so saves, reports, and mod-cache files stay local. Future captures include a receipt identifying source pins, ROM/route/binary hashes, and the requested diagnostic mode.

For an actual window rather than the automated dummy-video run:

```sh
local/build/demo-1-1/BrutalMarioDemo11SNESRecomp \
  --no-launcher --rom "$PWD/local/roms/demo-1-1.sfc"
```

This requires a working desktop display/audio environment and has not been manually playtested. The automated runs were under WSL2, not Windows-native builds.
